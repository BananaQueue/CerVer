# Project Brief: EMB Document Verification / Fetching System

## 1. Background

The Environmental Management Bureau (EMB) Region I issues a range of official documents (Special Orders, Travel Orders, Employee Accomplishment Reports, and likely others: permits, ECCs, CNCs, memos, communications). Currently, e-signatures on these documents can be easily cropped and pasted from one document to another, making fraudulent or tampered copies difficult to detect.

Each document already carries a **QR code**, generated by a system managed by EMB's central office / MIS (referred to as **IIS / EMBIS**, accessible at `iis.emb.gov.ph`). QR generation is **already solved** — it is not part of this project's scope.

**This project is the missing piece: a fetching/verification system.** Given a scanned QR (or its encoded ID/token), the system should retrieve the authoritative document details from the source database and display them, so anyone — public or internal staff — can confirm a printed or received document matches what was actually issued.

## 2. Problem Statement

- E-signatures are easily cropped/pasted onto forged or altered documents.
- There is no public-facing or internal way to instantly confirm a document's authenticity against the source record.
- We do not control or have full access to the system that generates documents and QR codes (IIS/EMBIS).
- We do not have direct database or API access to IIS.
- We do have:
  - An account on IIS with a **search bar for transaction numbers** (read-only for search; not privileged to view/download all documents).
  - A **local database** of documents, which **may be incomplete** relative to the full archive on IIS.

## 3. Goal

Build a **dynamic web-based verification app** that:
1. Accepts a scanned QR (or manually entered ID/token).
2. Looks up the corresponding document record — first in the local database, then falling back to a scoped, authenticated query against IIS's transaction search if not found locally.
3. Displays authoritative document details (type, control number, subject, date, signatory, status) so the person verifying can compare against the physical/printed copy.
4. Flags documents that are not found, expired, revoked, or superseded.
5. Progressively backfills the local database from IIS lookups to reduce future reliance on the live fallback.

**This is explicitly a workaround/hybrid system**, not a clean API integration — until/unless direct IIS database or API access is granted.

## 4. Findings From Sample Documents (as of this brief)

Three sample documents have been reviewed so far, all confirmed to contain a QR code:

| Document Type | Control Number Format | QR Location | Notes |
|---|---|---|---|
| Special Order (SO_2025_506.pdf) | `R1-2025-028799` (short alphanumeric) | Bottom-left corner, every page | Signed by Regional Director; contains long personnel lists — tampering risk includes adding/removing names |
| Travel Order (TO_Nov25_.pdf) | `EMBR1-2025-030436` | Near signature block | Contains approval dates, destination, purpose of travel |
| Employee Accomplishment Report | Long hash-like token embedded in URL (`13081688c1eb0a6ab8-69-2025-09-16-69-2025-09-30`), page footer shows `iis.emb.gov.ph/embis/dar/preview2/...` | Page 6 (last page), below "Submitted by" block — **not** in a consistent corner position like the other two types | Auto-generated via TCPDF from a live IIS web page; QR position varies by document type |

**Key implications:**
- **ID/token format is not uniform across document types.** The fetch/lookup logic must handle multiple formats (short codes vs. long hash tokens) rather than assuming one pattern.
- **QR placement on the page is not standardized** across document types — do not assume a fixed physical location when designing any OCR/QR-extraction tooling.
- IIS document preview pages follow a URL pattern: `https://iis.emb.gov.ph/embis/dar/preview2/{token}` — worth confirming whether QR codes always encode a full URL of this form, or sometimes just the bare control number/token.
- More document types are expected to be reviewed (permits, ECCs, CNCs, memos) — expect the schema to grow.

## 5. Proposed Architecture

```
Scan QR → extract ID/token
   → check local DB
        → found → return record, display status
        → not found →
             → authenticate session with IIS (stored credentials/session)
             → submit ID/token to IIS transaction search
             → parse search result page
             → cache parsed result into local DB
             → return record, display status
   → not found anywhere → display "no record found" (clear, non-technical message)
```

### Suggested stack
- **Backend:** Python + FastAPI
  - Chosen over Node/Express specifically because of the IIS fallback requirement — Python has strong tooling for scoped scraping/session-based requests (`httpx`/`requests`, and `Playwright`/`Selenium` if IIS search results are JS-rendered).
- **Database:** Match whatever engine the existing local database already uses (confirm: MySQL/PostgreSQL/SQLite). Do not introduce a new engine unnecessarily.
- **Frontend:** React (or plain HTML/JS if simplicity is preferred) — mobile-first scan-and-verify page using a client-side QR decode library (e.g. `html5-qrcode` or `jsQR`), no app install required.
- **Hosting:** Likely on EMB/DENR's existing server infrastructure (same environment as `iis.emb.gov.ph`), not public cloud, pending confirmation with MIS — data sovereignty likely matters for a government system. HTTPS is mandatory.

## 6. Key Features (MVP scope, roughly prioritized)

1. QR scan (camera-based, browser only) → decode → auto-lookup.
2. Manual ID/token entry fallback (in case scanning isn't available or QR is damaged).
3. Local DB lookup with clear "Verified ✅ / Not Found ⚠️" result page.
4. IIS fallback lookup (authenticated session, scoped to search-only privilege) when local DB misses.
5. Auto-caching of IIS fallback results into local DB (progressive backfill).
6. Status display: Active / Expired / Revoked / Superseded (as applicable per document type).
7. Verification attempt logging (timestamp, result, requester info if available) for audit/security purposes.
8. Public-facing simple view (no login) vs. internal staff view (authenticated, richer detail) — internal view can be phase 2.

## 7. Constraints & Open Questions to Resolve During Development

- **No direct IIS database/API access** — confirm this remains the case, or whether MIS can be asked for expanded access later.
- **IIS account privilege**: search-only, cannot view/download all documents — confirm exactly what fields the search result page exposes; this determines whether the fallback path is actually sufficient for verification purposes.
- **Session handling**: IIS login is likely cookie/session-based — needs secure credential storage and graceful re-authentication on session expiry.
- **Rate-limiting outbound requests to IIS** — must not hammer a shared system other staff rely on; add throttling/delays.
- **Parsing fragility** — since this relies on scraping a search result page rather than a real API, isolate parsing logic into one clearly separated module so it can be patched quickly if IIS changes its page layout.
- **Legal/procedural check** — confirm with MIS/IT admin that automated (rather than manual) use of the search account is acceptable under EMB's internal policy.
- **Local DB completeness** — confirm what percentage/date range of documents the local DB currently covers, to estimate how often the IIS fallback will actually be triggered.
- **Document types not yet reviewed** — permits, ECCs, CNCs, memos, communications — will need their schema/ID format confirmed as more samples are gathered.

## 8. Immediate Next Steps for Claude Code

1. Confirm local database schema (engine, tables, existing fields) — inspect if accessible.
2. Build FastAPI skeleton with a single endpoint: `GET /verify/{id_or_token}`.
3. Implement local DB lookup logic first (get this working end-to-end before adding the IIS fallback).
4. Investigate IIS's transaction search page structure (HTML source, whether JS-rendered) to determine whether `httpx`+`BeautifulSoup` suffices or `Playwright` is needed.
5. Build the IIS fallback module in isolation (single responsibility: given an ID, return parsed fields or None) so it can be swapped/patched independently.
6. Build the frontend scan page (React or plain HTML/JS) with `html5-qrcode`, wired to the `/verify` endpoint.
7. Add verification attempt logging table.
8. Add caching of fallback results into local DB.
